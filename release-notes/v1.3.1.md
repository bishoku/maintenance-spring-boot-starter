# v1.3.1 — Prevent message consumption during startup maintenance

In 1.3.0, Kafka and RabbitMQ listeners could consume messages before the startup
maintenance initializer paused/stopped them. This patch defers their first automatic
start until maintenance exit, closing that consumption window.

## Changes

- Defer managed listener startup after endpoint settings and user factory customizers
  have been applied, before the container reaches its first lifecycle start.
- Track the deferred containers separately. The first maintenance exit restores their
  automatic-start setting and starts them; listeners configured with `autoStartup=false`
  remain stopped. Failed starts retain ownership for retry.
- Preserve Kafka pause/resume and RabbitMQ stop/start in subsequent maintenance windows.
- Add local real-broker Kubernetes startup checks and retain the original 1.3.0 review
  evidence. Benchmark suites are not added to GitHub Actions.

## Upgrade and operating constraints

- Java 17+ remains required. Existing startup property names and defaults are unchanged.
  The initial deferral requires queue management and the relevant broker integration
  to be enabled. Kafka consumers join their group on the first maintenance exit.
- The guarantee covers listener endpoints created through Spring-managed factories during
  initial context startup. Custom factories and their `createListenerContainer` methods
  must be non-final, and must not start containers before returning them. Unsupported
  final factories fail initialization rather than silently bypassing deferral.
- Wait for startup initialization to complete before requesting maintenance exit. The
  previously identified early-exit race remains a known behavior.
- Avoid conflicting startup configuration sources: uppercase startup environment flags
  can override canonical false values; the property-precedence behavior is unchanged.
- Startup queue-stop errors are still logged without FAILED/partialFailure in the
  management snapshot. This patch does not change that reporting behavior.
- Kubernetes continues to own Service traffic routing. Use separate readiness/liveness
  probes and a pod-specific management route; no business HTTP filter is introduced.

See [operating instructions](../docs/operations.md#startup-maintenance) for details.

## Validation

- Java 17 source matrix: **188/188 tests passing** against each Boot 3.5.9 and 4.0.2 BOM.
- The same local candidate binary was consumed on MicroK8s with Boot **2.7.18, 3.5.9 and
  4.0.2**, Java 17: **438/438 startup checks** and **105/105 dynamic maintenance/routing
  regression checks** passed.
- All 15 startup cases observed zero messages before exit in both real Kafka and
  RabbitMQ; all eight seeded messages per broker were processed after exit. User-disabled
  listeners remained stopped, and a second maintenance cycle passed.

The [validation report](../benchmark/reports/STARTUP_CONSUMPTION_FIX.md) records exact
candidate hashes, scope and raw evidence. Local 1.3.1 packaging passed another 188 tests;
its 39 non-Maven entries (including 36 classes) are byte-identical to the tested candidate.
Candidate results are not presented as a test of the signed Central JAR.
