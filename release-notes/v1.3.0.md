# v1.3.0 — Startup maintenance mode and dynamic Actuator exit

This minor release adds support for booting Spring Boot applications directly in maintenance
mode via configuration (for example during Kubernetes platform migrations, pre-cutover
verification, or dark launches) and dynamically exiting maintenance mode via the Actuator
endpoint once verification is complete.

## Changes

- Add configuration properties `maintenance.start-in-maintenance` and `maintenance.startup.enabled`
  (with environment variable support `MAINTENANCE_START_IN_MAINTENANCE` and `MAINTENANCE_STARTUP_ENABLED`),
  plus `maintenance.startup.reason` (`MAINTENANCE_STARTUP_REASON`).
- Initialize `MaintenanceState` directly in the `ACTIVE` phase (`isMaintenanceActive() == true`
  and `isWorkBlocked() == true`) upon bean creation when startup maintenance is enabled.
- Add `MaintenanceStartupInitializer` to enforce `ReadinessState.REFUSING_TRAFFIC` (`503 OUT_OF_SERVICE`)
  on startup with zero drain delay while keeping `LivenessState` healthy (`UP`), and to pause/stop
  managed Kafka and RabbitMQ listener containers into the starter's owned registry on startup.
- Support dynamic exit from startup maintenance mode via `POST /actuator/maintenance` with
  `{"enabled":false}`, running exit hooks, resuming managed Kafka/RabbitMQ consumers, and
  restoring readiness to `ACCEPTING_TRAFFIC` (`200 OK`) without restarting the pod.
- Preserve existing `@Scheduled` task infrastructure at the framework level so application jobs
  consulting `MaintenanceState.isWorkBlocked()` observe active maintenance mode from their first tick.
- Add unit, end-to-end, and concurrent stress test suites covering startup maintenance mode,
  readiness event ordering, queue lifecycle transitions, and dynamic Actuator exit.

## Upgrade notes

- **Fully backward-compatible with 1.2.x.** `maintenance.start-in-maintenance` and
  `maintenance.startup.enabled` default to `false`, preserving standard startup behavior unless
  explicitly enabled.
- When `maintenance.start-in-maintenance=true` (or `maintenance.startup.enabled=true`), the pod
  starts with `/actuator/health/readiness` returning `503 OUT_OF_SERVICE` while
  `/actuator/health/liveness` remains `200 OK`. Ensure your Kubernetes `livenessProbe` targets
  `/actuator/health/liveness` and not the combined `/actuator/health` endpoint.
- Use a pod-specific route (such as direct Pod-IP from an authorized in-cluster client) to call
  `POST /actuator/maintenance` with `{"enabled":false}` when ready to bring the pod into live
  Service rotation.

## Validation

Verified with `mvn --batch-mode clean verify` across Spring Boot 3.5.9 and 4.0.2 (177 tests passing,
0 failures, 0 errors), covering startup configuration variants, readiness probe interception,
Kafka/RabbitMQ startup pause and dynamic resumption, `@Scheduled` non-interference, and
concurrent cold-boot stress tests.
