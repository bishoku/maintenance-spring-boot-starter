# v1.2.0 — Readiness lifecycle reliability and Spring Boot 4 compatibility

This minor release strengthens maintenance transitions and verifies the same starter
binary with Spring Boot 3.5.9 and 4.0.2. Kubernetes remains responsible for Service
routing; the starter changes readiness and keeps its management endpoint available
through a pod-specific route.

## Changes

- Use the Actuator access model supported by Boot 3.5/4, including optional maintenance reasons.
- Report transition phases and partial failures; preserve the last confirmed mode and support retry.
- Run exit hooks before consumers resume; withhold readiness acceptance after critical failure.
- Cancel timed-out hooks cooperatively and block overlapping transitions while a timed-out hook still runs.
- Await Kafka pause/resume acknowledgement, handle consumers without assigned partitions,
  and inspect concurrent container children individually. Preserve external pause ownership.
- Await RabbitMQ listener stop callbacks, preserve previously stopped listeners and compensate partial resume failures.
- Preserve broker error details and record failed transition metrics accurately.
- Add local Compose and MicroK8s correctness benchmarks, a selectable Boot sample and before/after reports.
- Add contribution, support, security and community guidance; simplify the README.
- Update the Central publishing plugin to 0.12.0 for Maven 3.10-compatible staging.
- Publish GitHub releases with reviewed notes, JAR/source/Javadoc/POM artifacts, signatures and SHA-256 checksums.

## Upgrade notes

- **The source baseline moves to Spring Boot 3.5.9, with Java 17 minimum.** Earlier Boot
  lines are not supported by this release. Tested combinations are Boot 3.5.9 and 4.0.2
  with Java 17 and 25; this is not a claim about every 4.x release.
- Enable the endpoint with `management.endpoint.maintenance.access=unrestricted`
  and include `maintenance` in web exposure. Use `read-only` for status-only access.
  Do not set both the legacy endpoint `enabled` property and `access`.
- HTTP 200 acknowledges a management operation, not transition success. Inspect
  `details.phase` and `details.partialFailure`. Failed attempts no longer claim completion;
  events may carry failure reports and `active` retains the last confirmed state.
- Exit hooks now prepare the application **before** broker consumption resumes. Make hooks
  bounded, interruptible and idempotent; failed transitions can repeat them on retry.
- `maintenance.queue-timeout` bounds acknowledgement waiting (default 30 seconds).
  `drain-delay` is readiness propagation grace, not an HTTP drain barrier.
- Keep a pod-specific management route available while the application Service excludes
  the pod. No HTTP filter or restart-persistent maintenance state is introduced.

## Validation

Before release packaging: 83 source tests passed for each Boot 3.5.9/4.0.2 and Java 17/25
combination; 64 Compose checks and 68 real MicroK8s checks passed. Kubernetes checks include
management reads and successful exit while one or all application pods are unready.
The 1.2.0 versioned package also passed both Boot source suites (83 tests each).
These benchmarks run locally and are not added to GitHub Actions.

See [validation details](https://github.com/bishoku/maintenance-spring-boot-starter/blob/v1.2.0/benchmark/reports/READINESS_CONTRACT.md)
and the [full comparison](https://github.com/bishoku/maintenance-spring-boot-starter/compare/v1.1.1...v1.2.0).
